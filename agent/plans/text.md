## Главное ограничение
Go отлично подходит для **бэкенда и общей бизнес-логики**, но **не для UI мобильного приложения**. Нативных Go-фреймворков для iOS/Android с нормальным UI нет. Поэтому есть два честных пути:

| Вариант | Клиент | Go используется | Когда выбирать |
|---|---|---|---|
| **A. Гибрид (рекомендую)** | Flutter | бэкенд + синхронизация | нужны iOS и Android, один разработчик |
| **B. gomobile** | Kotlin/Swift + Go-core | бэкенд + общая логика через gomobile | есть мобильные разработчики, нужен Go везде |
| **C. Только Android** | Kotlin | бэкенд | iOS не нужен, экономим время |

Для дедлайна 30.11 и соло-разработки — **вариант A**.

## Архитектура (вариант A)

```
┌─────────────────────────────┐
│  Flutter (iOS / Android)    │
│  ├─ UI (Dart)               │
│  ├─ Local DB: SQLite/Drift  │  ← источник истины для UI
│  └─ Sync engine (Dart)      │
└──────────┬──────────────────┘
           │ HTTPS / JSON (или protobuf)
┌──────────▼──────────────────┐
│  Go backend                 │
│  ├─ chi / echo              │
│  ├─ PostgreSQL (pgx/sqlc)   │
│  ├─ JWT auth                │
│  └─ Sync API (push/pull)    │
└─────────────────────────────┘
```

**Ключевой принцип: offline-first.** Приложение работает **полностью без сети**, а синхронизация — фоновая и необязательная. Это снимает риск «приложение бесполезно без интернета».

## Как реализовать офлайн-режим

### 1. Локальная БД — источник истины для UI
- Flutter: **Drift** (SQLite) или **Isar**. Drift предпочтительнее — SQL, миграции, типы.
- Все операции (добавить расход, изменить категорию, удалить) пишутся **сначала локально**, потом ставятся в очередь на синк.
- Ни одного экрана, который требует сети.

### 2. Очередь исходящих изменений (outbox)
Таблица `pending_operations`:
```
id, entity_type, entity_id, operation (create/update/delete),
payload (JSON), created_at, retry_count
```
Синк-движок раз в N минут / при появлении сети / при запуске прогоняет очередь. После успеха — удаляет из очереди.

### 3. Разрешение конфликтов
Для приложения учёта расходов достаточно **last-write-wins по `updated_at`**:
- каждая запись имеет `id` (UUID v4, генерируется на клиенте), `updated_at`, `deleted_at` (soft delete);
- сервер при push сравнивает `updated_at` и оставляет более свежую версию;
- клиент при pull обновляет локальные записи, если серверная версия новее.

CRDT не нужны — данные почти не редактируются параллельно с двух устройств у одного студента.

### 4. Идентификаторы
UUID v4 на клиенте. Не auto-increment с сервера — иначе офлайн-создание ломается.

### 5. Auth в офлайне
- Первый логин — онлайн, получаем `access_token` (короткий) + `refresh_token` (долгий).
- Токены хранятся в secure storage (Keychain / Keystore).
- Без сети — работаем по кэшированному refresh_token, если он не истёк (например, 30 дней).
- Если истёк и сети нет — приложение всё равно работает локально, просто синк отложится.

### 6. Медиа и вложения
В MVP — не хранить чеки. Если всё же нужно: файлы в S3-совместимое хранилище (MinIO/Cloudflare R2), локально — в файловой системе, синк отдельной очередью.

## Go-бэкенд: конкретика

**Библиотеки:**
- роутер: `chi` (лёгкий, идиоматичный)
- БД: `pgx` + `sqlc` (типизированные запросы без ORM-магии)
- миграции: `golang-migrate`
- валидация: `go-playground/validator`
- логи: `zap` или `slog` (встроен в Go 1.21+)
- конфиг: `envconfig` + `.env`
- тесты: `testify` + `testcontainers-go`

**API (REST, можно потом перейти на gRPC):**
```
POST /auth/register
POST /auth/login
POST /auth/refresh

POST /sync/push      ← массив операций от клиента
GET  /sync/pull?since=<timestamp>   ← изменения с сервера

GET  /categories
GET  /limits
```
Логику синхронизации лучше свести к **двум эндпоинтам** — это резко упрощает и клиент, и сервер.

## Риски, специфичные для этого стека
1. **Sync — самая сложная часть.** Заложить на неё 4–6 недель, а не 1.
2. **Схема БД на клиенте и сервере разъедется.** Помогают миграции Drift + версионирование API.
3. **`gomobile` усложняет сборку** (CI, размер бинарника, отладка). Не брать без необходимости.
4. **«Офлайн» не равно «нет сервера».** Даже с офлайн-first нужен аккаунт и синк, иначе при потере телефона данные теряются.
5. **Flutter — не Go.** Если цель «всё на Go», дедлайн 30.11 нереалистичен.
